# 역사 Quiz 미션 수행

미션2(파이썬 처음배우기) 수행을 위한 "한국 역사 퀴즈 게임"이다. 한국사를 주제로 하고, 분야·난이도 선택, 무작위 출제, 힌트, 해설, 점수 및 JSON 기록 저장을 지원한다.

> **제출 상태 (2026-11-15):** 실행 검증 자료는 `docs/testing/`에, 실제 원격 clone/pull 및 Git 이력 로그는 `docs/git-evidence/commands.txt`에 있다. 사전 평가의 문서 누락을 보완했다. 다만 원격의 10개 이상 커밋 및 실제 병합 기록은 보완중이다.

| 분야 | 난이도 | 문제 수 | 예시 주제 |
|---|---|---:|---|
| 역사 | 초급 | 3 | 조선·고려 건국, 훈민정음 |

## 4. 주요 기능

1. **퀴즈 풀기:** 분야(전체/역사/문화), 난이도(전체/초급/중급), 문제 수 선택
2. **랜덤 출제:** `random.sample()`로 문제 중복 없이 무작위 출제
3. **힌트:** `H` 입력으로 문제당 한 번 확인
4. **정답과 해설:** 답변 직후 정답 여부와 설명 표시
5. **점수:** 힌트 없이 정답 10점, 힌트 사용 후 정답 7점, 오답/건너뛰기 0점
6. **문제 추가·목록·삭제:** 메뉴에서 문제를 관리하고 JSON에 저장
7. **최고 점수·게임 기록:** `state.json`에 저장하여 재실행 시 불러오기
8. **예외 처리:** 잘못된 입력, 파일 읽기·쓰기 오류, Ctrl+C 종료 처리

**최종 점수:** `round(획득 점수 / (출제 문제 수 × 10) × 100)`

예: 5문제 중 힌트 없이 3개 정답, 힌트 사용 후 1개 정답, 1개 오답이면 37/50점, 최종 "74점" 이다. 이 예시는 계산에 대한 설명이다.

## 6. 클래스 설명

| 클래스 | 주요 역할 |
|---|---|
| `Quiz` (`quiz.py`) | 문제·선택지·정답·힌트·해설·분야·난이도 보관, 점수 계산, JSON 변환 |
| `QuizGame` (`quiz_game.py`) | 메뉴, 입력 검증, 랜덤 출제, 문제 추가·삭제, 점수 및 기록 저장 |

`Quiz.to_dict()`는 객체를 딕셔너리로 바꾸고, `Quiz.from_dict()`는 저장된 딕셔너리에서 객체를 다시 생성한다. `QuizGame.load_state()`는 JSON 파일을 읽고 `save_state()`는 UTF-8 JSON 파일을 기록한다.

### 객체지향 설계를 선택한 이유와 장단점 (평가 #13)

`Quiz`는 한 문제의 데이터와 검증·채점 동작을 묶는다. 생성 시 `__post_init__()`가 선택지 4개와 정답 범위를 검사하므로, 문제를 생성하는 여러 경로에서 같은 규칙을 재사용할 수 있다. `QuizGame`은 `quizzes`, `best_score`, `history`를 인스턴스 상태로 보관해 메뉴 동작 사이에 유지한다. 예를 들어 `play()`가 갱신한 최고 점수와 기록을 같은 객체의 `save_state()`가 저장한다. 전역 변수를 여러 함수에서 수정하는 방식보다 상태의 소유자와 책임을 찾기 쉽다.

함수 기반 구현도 상태 딕셔너리를 인자로 전달하면 전역 변수 없이 같은 기능을 만들 수 있으며, 작은 프로그램에서는 더 간단하다. 여기서는 문제 단위 검증과 게임 상태 관리를 반복 사용하므로 클래스로 묶었습니다. 대신 클래스는 `self`와 초기화 과정을 이해해야 하고, 현재 `QuizGame`은 입력·출력과 파일 저장까지 담당하므로 독립적인 테스트가 번거롭다. 또한 `defaults.copy()`는 복사이므로 문제 객체 자체의 수정까지 격리하지는 않는다. 규모가 커지면 입력·출력과 저장을 별도 구성 요소로 분리할 수 있다.

## 7. JSON 데이터 구조

`state.json`은 첫 실행 시 생성되며 다음 구조를 가진다.

```json
{
  "quizzes": [
    {
      "question": "조선을 건국한 인물은?",
      "choices": ["왕건", "이성계", "세종", "정조"],
      "answer": 2,
      "hint": "조선의 초대 왕입니다.",
      "explanation": "이성계는 1392년에 조선을 건국했습니다.",
      "category": "역사",
      "level": "초급"
    }
  ],
  "best_score": 0,
  "history": []
}
```

위 코드는 구조 설명을 위해 퀴즈 목록을 1개로 줄인 "예시" 이다. 실제 기본 문제는 12개 이다.

| 필드 | 목적 | 예시 |
|---|---|---|
| `quizzes` | 문제 객체를 복원할 데이터 목록 | 위 예시의 문제 1개 또는 기본 12개 |
| `best_score` | 모든 게임 중 최고 최종 점수(0~100) | 첫 실행 `0`, 만점 획득 후 `100` |
| `history` | 플레이 일시·분야·난이도·문제 수·정답 수·점수 기록 | 첫 실행 `[]`, 이후 `{"played_at":"2026-11-15 12:00:00","category":"역사","level":"초급","questions":1,"correct":1,"score":100}` 같은 객체의 목록 |

### JSON 저장 방식의 한계 (평가 #18)

현재 방식은 로드 시 JSON 전체를 문자열과 객체 목록으로 메모리에 올리고, 저장할 때 전체 데이터를 다시 직렬화 한다. 문제 수와 게임 기록이 늘면 읽기·쓰기 시간과 메모리 사용량이 증가하며, `indent=2`는 가독성을 높이는 대신 파일 크기도 늘린다. 기록은 자동으로 정리되지 않아 계속 증가한다.

임시 파일 교체는 저장 중 불완전한 파일 노출을 줄이지만, 파일 잠금이나 여러 실행 간 트랜잭션을 제공하지 않는다. 동시에 실행하면 나중에 저장한 내용이 앞선 변경을 덮어쓸 수 있다. 개인용 소규모 학습에는 적합하지만, 대량 데이터·검색·동시 실행이 필요하면 SQLite처럼 필요한 행만 조회·수정하고 트랜잭션을 지원하는 DB로 전환하는 것을 권장한다. 여러 사용자가 접속하는 서버라면 서버용 DB와 접근 제어도 필요하다.

저장 시 임시 파일(`state.json.tmp`)에 먼저 쓴 뒤 교체한다. JSON 오류가 발견되면 기존 파일을 자동으로 덮어쓰지 않고 기본 문제로 시작하도록 설계했다. 단, 이후 게임을 진행해 저장하면 기존 파일이 교체될 수 있으므로 "테스트 전 백업이 필수" 이다.

### 9.1 커밋 단위와 메시지 규칙 (평가 #12)

커밋 하나에는 검토·되돌리기가 가능한 한 가지 목적의 변경을 포함한다. 예를 들어 퀴즈 기능 추가와 README 오타 수정은 분리하고, 기능을 성립시키는 관련 수정과 검증은 함께 묶는다. 커밋 수를 채우기 위한 빈 커밋이나 의미 없는 파일 분할은 하지 않는다. 커밋 전 `git diff`와 관련 실행 결과를 확인하고 개인 테스트 파일이나 임시 저장 데이터가 포함되지 않게 한다.

메시지 형식은 `<type>: <변경 내용>`이며 필요하면 빈 줄 뒤에 이유와 검증 방법을 적습니다. 이후 작업에 적용하는 규칙이며 과거 메시지를 다시 썼다는 의미는 아니다.

| type | 사용 목적 | 메시지 예시 |
|---|---|---|
| `feat` | 새 기능 | `feat: 시대별 퀴즈 선택 추가` |
| `fix` | 오류 수정 | `fix: 잘못된 저장 데이터 처리 수정` |
| `docs` | 문서 보완 | `docs: JSON 저장 한계 설명 추가` |
| `refactor` | 동작을 유지한 구조 개선 | `refactor: 파일 저장 책임 분리` |
| `test` | 검증 시나리오 추가 | `test: 힌트 사용 시 채점 검증 추가` |
| `chore` | 개발 설정 정리 | `chore: 임시 검증 폴더 제외` |

### 9.2 브랜치 분리 이유와 병합 정책 (평가 #16)

앞으로는 안정적으로 실행되는 통합본을 `main`에 유지하고 `feature/<주제>`, `fix/<주제>`, `docs/<주제>`에서 각각 작업한다. 브랜치를 분리하면 진행 중인 수정이 통합본에 바로 영향을 주지 않으며, 변경 범위를 비교하고 검증하기 쉽다. 병합은 분리된 작업을 통합본에 반영하는 과정이다.

변경 전 `git fetch origin`으로 원격 상태를 확인하고 통합 브랜치에서 작업 브랜치를 만든다. 작업 후 관련 실행 검증과 diff 검토를 거쳐 PR 또는 로컬 `git merge --no-ff <작업 브랜치>`로 통합한다. `--no-ff`는 작업 브랜치의 통합 지점을 병합 커밋으로 남긴다. 충돌은 변경 의도를 확인해 해결한 뒤 다시 검증하며, 공유 브랜치의 강제 push와 이력 재작성은 피한다. 병합 후 검증과 원격 반영을 확인하고 작업 브랜치를 정리한다.

이 내용은 **향후 적용할 정책** 이다. 현재 원격에는 `main`과 `master`가 별도 이력으로 존재하며 실제 병합 기록은 없다. 두 브랜치를 자동 병합해도 안전하다는 뜻은 아니므로 공통 조상과 파일 차이를 먼저 검토해야 한다.
